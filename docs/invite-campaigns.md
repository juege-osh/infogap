# 活动邀请码

一个活动使用一个共享邀请码。固定邀请码长期有效、不限注册次数，直到站长撤销；普通邀请码按配置的次数和期限使用。名单内外的邮箱都能凭有效邀请码，按原有流程获取邮箱验证码并注册。只有名单内的首次注册账户获得活动奖励；已有账户登录不会补发。普通新账户初始永久积分为 0，仍按黑铁规则每天获得 1 点赠额。

本次活动配置为青铜权益 30 天、一次性永久积分 1000 点。青铜期间每日赠额为 2 点；30 天后恢复用户自身贡献或有效付费段位对应的权益。1000 点进入永久余额，活动结束不清零。活动不增加贡献度，不生成支付订单，也不发放付费段位的每期赠分。

## 站长接口

`POST /api/admin/invites` 保留普通邀请码的 `max_uses`（1–100）和 `days`（1–90）。设置 `permanent:true` 则创建固定邀请码，服务端不再检查次数和期限；传入的 `max_uses`、`days` 会被忽略。固定活动邀请码示例：

```json
{
  "permanent": true,
  "emails": ["member@example.org"],
  "reward_rank": "bronze",
  "reward_days": 30,
  "reward_credits": 1000
}
```

示例邮箱仅为演示。实际名单通过站长后台或站长身份接口提交，不放进源代码、前端、URL、公开接口或日志。邮箱会去除首尾空格、转为小写并去重；每次最多输入 1000 个有效邮箱，请求正文上限为 320 KiB，其他 API 的大小限制不变。当前活动段位仅支持 `bronze`，期限可设 1–365 天，永久积分可设 1–100000。`days` 是邀请码有效期，`reward_days` 是每位成功注册者的权益期限，两者独立计算。

固定邀请码的 `uses` 仍记录成功注册人数，但没有数量上限，数据库以 `permanent=1` 明确保存此规则，`max_uses=0`、`expires_at=""` 只是配套空值，不是零名额或已过期。普通邀请码的使用次数是全部注册者共享的上限，名单外注册同样占用次数；名单数量不会自动扩大普通邀请码容量。

创建返回 `id`、`code`、`expires_at`、`permanent` 及 `campaign` 奖励概况。固定邀请码和活动邀请码只在这次创建响应中显示，站长应保存后再分享；后续后台列表与活动详情不返回该码。原有撤销接口仍为 `POST /api/admin/invites/{id}/revoke`。撤销同时阻止之后获取验证码和使用已发验证码完成新注册，已经发放的权益保持原有效期。

`GET /api/admin/invites/{id}/campaign` 仅站长可读，返回 `permanent`、奖励配置、`email_count`、`awarded_count` 和 `emails` 数组。每项包含 `email`、`awarded`、`awarded_at`、`rank_until`。审核员和普通成员不能读取名单。没有活动配置的邀请码返回 404。

## 发放与备份

验证邮箱、消费邀请码次数、创建账户、记录永久积分流水、保存唯一奖励记录和创建会话，都在同一注册事务内完成。任一步失败，注册和奖励一起回滚。验证码不能重复使用；并发验证或重复登录不会重复发奖、延长权益或再次消耗邀请码次数。

活动数据位于 `invite_campaigns`、`invite_campaign_members`、`invite_campaign_awards`。每个用户最多一条注册奖励，每个活动邮箱也最多领取一次。活动青铜权益单独保存，只在计算有效段位时与已购买段位合并；不会写入每期赠分表。

升级为旧库新增 `invites.permanent`，默认 0，原邀请码的剩余次数、到期时间和使用记录保持不变。固定码的长期有效不延长每位成员的青铜期限；奖励始终从该成员实际注册成功时计算 30 天（或活动配置的期限）。

备份应包含整个 SQLite 数据库，保留邀请码、私密名单、奖励记录和积分流水之间的关系。部署不会预创建名单用户、自动发送邮件或给已有账户补发奖励。
